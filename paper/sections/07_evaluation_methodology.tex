\section{Evaluation Methodology}

\subsection{Benchmarks and provenance}

The initial study follows the AreCELearnedYet single-table benchmark lineage
and currently includes Census13, Forest10, Power7, and DMV11. Dataset adapters
validate source archive and content hashes, construct typed PostgreSQL tables,
and extract audited workloads. Each run keeps the \texttt{AdvisorSnapshot}
separate from its bound \texttt{GroundTruthSet}. The latter is an independent
utility input, not a snapshot field and not an input to native statistics
construction. The benchmark data root is selected through
\texttt{EXTSTATS\_RESEARCH\_DATA\_ROOT}, so an absolute local path is not part
of semantic run identity.

Every canonical RunManifest records the research repository and committed
research SHA, advisor repository and SHA, patched PostgreSQL repository and
SHA, stock PostgreSQL version or commit, dataset and workload identity, sample
rows and seed, statistics target, candidate limit, search budget, and relevant
experiment parameters. Canonical runs require a clean research working tree;
uncommitted experiment provenance is invalid.

\subsection{System roles and sample policy}

Stock PostgreSQL is the baseline and deployment target. The patched tree is
used only for design-time catalogless planner evaluation. A fixed typed sample
is created once per canonical run; native payloads are independently rebuilt on
the full database for transfer experiments. Ordinary statistics target,
sampling parameters, and relation population are held fixed within each
comparison. Ground truth is not used to build the sample or native payloads.
The design-time protocol is deterministic once the sealed snapshot/sample,
native repository, workload, candidate ordering, planner settings, and bound
truth are fixed. By contrast, stock deployment uses native
\texttt{CREATE STATISTICS} followed by \texttt{ANALYZE}; PostgreSQL's native
sampling is a stochastic realization. The experiment seed statement is not a
claim that a fresh \texttt{ANALYZE} is bit-identical across runs, and no
\texttt{setseed} setting is treated as proof of native-statistics
replayability.

\subsection{Truth acquisition and binding}

The current \texttt{GroundTruthSet} contract has two source kinds. The
confirmatory AreCEL policy uses \texttt{authoritative-external-exact} for
Census13, Forest10, Power7, and DMV11. For
\texttt{production-exact-execution}, capture and eligible truth acquisition
run in a read-only repeatable-read source view. The v1 wrapper counts only
sealed \texttt{postgresql-simple-selection-v2} queries: one base relation,
supported AND predicates, and row-preserving direct-column/star projection.
Distinct, grouping, aggregates, windows, LIMIT/OFFSET, ORDER BY, locking,
arbitrary projection expressions, and unresolved parameters fail closed before
count execution. Exact count collection can be expensive on large relations;
read-only is not zero cost. For \texttt{authoritative-external-exact}, immutable
labels are imported and validated against the sealed snapshot semantic digest,
workload ID, positive-weight query coverage, and source artifact SHA-256. The
advisor does not claim to have executed those labels. All four AreCEL datasets
use this external source kind and bind the AreCELearnedYet base:test workload
and label identity. Census13 additionally has a one-time full equivalence audit
against an existing production-exact canary; this audit creates no new
10,000-query PostgreSQL collection. The remaining datasets are currently
provenance-validated rather than claimed to have independently re-executed
full equivalence. Production exact execution remains an explicit
validation/cost path, not the repeated confirmatory default.

\subsection{Metrics and comparisons}

RQ1 compares stock PostgreSQL 16, a strong conventional statistics baseline,
simple selection heuristics, and \advisor. The baseline protocol is explicit
but remains dataset-specific: use stock PostgreSQL, no extended statistics,
and execute \texttt{SELECT setseed(1.0 / 123)} before one \texttt{ANALYZE};
the experiment seed identifier is 123 and the setseed argument is the floating-
point expression \texttt{1.0 / 123}. Use target 10000 on every benchmark
column where the AreCELearnedYet paper-baseline artifact defines that setting.
The current Census13, Forest10, Power7, and DMV11 baseline manifests all
record one \texttt{ANALYZE}, the exact setseed statement above, and target
10000; the
legacy Census13 artifact stores the target at the baseline level, whereas the
newer artifacts also expose more column-level verification.
For DMV11, this means all eleven columns at target 10000, one analyze, no
extended-statistics objects, experiment seed identifier 123, the exact
setseed statement above, the external exact label source, and 10,000 base:test
queries. If a dataset's audited baseline artifact uses a
different documented configuration, preserve that configuration and record it
instead of silently forcing uniformity. RQ1 reports arithmetic mean q-error,
p50, p95, p99, maximum, and improved/unchanged/worsened counts. Published
learned-CE results from \cite{Wang2021AreWeReady} are a clearly labeled
literature/contextual reference, not a head-to-head experiment under identical
systems and workloads. A gap-closure metric is reported only if the metric and
workload correspondence can be demonstrated.

RQ2 uses the existing full-data transfer protocol. P0 is a fresh full-data
baseline before deployment. P1 deploys the immutable Recommendation and runs
the final \texttt{ANALYZE}. P2 preserves the same ordinary-statistics state,
removes exactly the advisor-managed objects in a research-only transaction,
measures without \texttt{ANALYZE}, and rolls back. P1/P2 ordinary-statistics
fingerprints are expected to match; P0 can differ because deployment's final
\texttt{ANALYZE} refreshes the relation. The fixed-sample objective is
$J_S(M)$, while a full-data result is written $J_D(M;A)$ for one native
\texttt{ANALYZE} realization $A$. The observed difference therefore combines
sample-to-full-data transfer with native realization variability; it is not a
mechanism-fidelity measurement.

RQ3's primary comparison removes the binary/build confound: compare physical
statistics with catalogless hypothetical statistics using the same patched
PostgreSQL binary. It controls relation contents, schema, workload, ordinary-
statistics fingerprint, statistics target, equivalent design, equivalent
payload semantics (and identical payload bytes where technically possible),
and planner/session settings. The intended main factor is only physical
catalog realization versus hypothetical overlay realization. The primary
metrics are exact root \texttt{Plan Rows} agreement, mismatch count, and
mismatch classification; no near-exact threshold is pre-registered without
empirical justification. Objective difference is derived, while q-error
correlation is only a secondary diagnostic. A
synthetic Priority-0 harness exercises this comparison independently for MCV
only, dependencies only, and MCV-plus-dependencies configurations; it records
payload non-emptiness, supported clause forms, and observed changes relative to
the no-extended-statistics baseline without claiming planner-consumption
instrumentation. A
secondary sanity check compares patched PostgreSQL physical statistics with
stock PostgreSQL physical statistics with the overlay inactive; this is not
the primary hypothetical-fidelity comparison. If the current build setup
cannot run both realizations on the same patched binary, the experiment is
implementation-needed and the blocker is recorded rather than changing DBMS
	semantics. Sample-to-full-data utility belongs to RQ2, not this
mechanism-fidelity question.

RQ4 is split into two evidence layers. RQ4a is the primary deterministic
design-time comparison on the patched planner: random-k, workload-frequency
top-k, native-payload-size top-k, singleton-utility top-k, and greedy ADD;
exhaustive search is a separately reported tiny-universe diagnostic only. All
methods use the same sealed snapshot, sample native repository, eligible
universe, planner/settings, workload, truth/loss contract, and canonical
ordering. The fixed-k protocol uses $k=4$ independently of the advisor
recommendation. Random-k has five pre-registered seeds $(1,2,3,4,5)$; each
replicate uses the same universe and reports individual results plus
mean/standard deviation/minimum/maximum. RQ4a reports objective, membership,
object count, configuration evaluations, PostgreSQL planner calls,
preprocessing, selection wall time, termination status, overlap, and tiny
exhaustive optimality gap. Its deterministic replay smoke must reproduce
membership, evaluation order, planner estimates, objectives, and traces
exactly apart from runtime measurements.

RQ4b is secondary: it measures the physical consequence after stock
\texttt{CREATE STATISTICS} and native \texttt{ANALYZE}. It is explicitly a
stochastic native-statistics realization and must not redefine or replace
RQ4a. The controlled smoke builds the union of method selections once,
performs one shared stock \texttt{ANALYZE}, and clones that analyzed parent;
each clone drops statistics not selected by its method without another
\texttt{ANALYZE}, verifies that kept payload bytes are unchanged, and runs
full/small EXPLAIN evaluation. This controls a common native realization for
method comparison. A separate planned
\texttt{native-analyze-stability-v1} protocol uses five independent native
realizations to quantify variability; it does not claim that the seed
statement controls \texttt{ANALYZE}.

The RQ4 primary eligible universe is frozen using only native kind, schema
validity, sample payload availability, and predeclared compatibility;
utility/outcome screening is a separate conditional diagnostic. Its statuses
distinguish exactly-$k$ completion, at-most-$k$ local optimum, budget
censoring, and genuine infeasibility. The fixed-evaluation-budget mode remains
implementation-needed and, when implemented, will cap
configuration-objective evaluations at 2,000 and elapsed selection time at
300 seconds. A configuration evaluation may contain many PostgreSQL
per-query planner calls, so both quantities are recorded separately;
selection preprocessing, singleton profiling, final evaluation, native
realization, and physical evaluation are separate cost stages. Independent
stock full-data evaluation is outside the selection budget. Cheap methods
cannot inspect GroundTruthSet during selection; singleton and greedy methods
use the same bound truth, and all methods receive the same later stock
full-data evaluation. RQ5 measures snapshot and truth acquisition, sample
size, native construction, planner search, deployment DDL/\texttt{ANALYZE},
storage, planning-time change, and refresh cost. We do not claim zero online
overhead; the narrower statement is that no separate learned-model inference
path is added to production query processing.

Truth acquisition is reported separately from other design-time costs:
authoritative external truth contributes import and validation cost, whereas
production exact truth contributes the cost of exact-count collection. The
overall accounting therefore includes sample capture, truth acquisition,
native statistics construction, planner search, and deployment \texttt{ANALYZE}.

\subsection{Preliminary versus confirmatory evidence}

Existing Census13, Forest10, Power7, and DMV11 runs are pilot/preliminary
evidence that the end-to-end pipeline and full-data validation path work. The
paper will only promote a result to a final claim when its immutable raw and
derived artifacts, manifest, and source identities pass the repository audit.
The current results section therefore defines schemas and TODOs rather than
inventing values.

\subsection{Reproducibility}

The research harness stores compact derived evidence while referring to large
immutable bundles by run ID and digest. Reproduction starts from a clean
committed research SHA, verifies advisor and PostgreSQL identities, reconstructs
the frozen input artifacts, and reruns the declared experiment command. The
paper's companion experiment plan is the specification for the missing
confirmatory runs.
