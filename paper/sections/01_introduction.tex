\section{Introduction}

Cardinality estimation is a small interface with system-wide consequences. A
query optimizer uses estimated result sizes to compare access paths, join
orders, and operator implementations; an estimate that is wrong by orders of
magnitude can therefore induce a bad plan even when the execution engine is
otherwise sound \cite{Leis2015HowGood}. PostgreSQL's ordinary statistics are
compact and usually maintained per column, so they cannot represent every
cross-column correlation in a workload. Native multivariate statistics provide
an existing corrective mechanism for selected column groups \cite{PostgreSQL16Docs}.

Learned cardinality estimators demonstrate that the accuracy gap can be large,
but they also make training or update cost, inference cost, staleness,
interpretability, and behavior under changing data part of the deployment
question \cite{Wang2021AreWeReady}. We study a less disruptive alternative:
design the native extended statistics already consumed by PostgreSQL's
estimator rather than replacing that estimator.

The design problem is nontrivial. Given a workload and schema, a candidate
universe contains many possible column pairs and native kinds, while each
candidate must cover useful predicates, be materialized at an adequate target,
and interact with PostgreSQL's native selection and combination rules. The
advisor must choose a membership and an order under a finite search budget;
creating every candidate and evaluating every subset is not a practical design
loop for the supported workload scope.

A straightforward physical loop makes this harder to control: choose a
configuration, issue \texttt{CREATE STATISTICS}, run native \texttt{ANALYZE},
plan the workload, change the catalog, and repeat. The loop mutates catalog
state, repeats native payload construction, entangles configuration choice with
sampling realization, and grows combinatorially. A stock shared-parent-and-
clone experiment can reuse one analyzed realization for several physical
configurations, but that is an experimental control technique, not a lightweight
catalogless activation interface for repeated search.

Our key insight is to separate native payload construction from configuration
evaluation. \advisor builds a typed fixed sample once, materializes each
candidate's native MCV or dependency payload once, and registers those
payloads in a backend-local patched PostgreSQL repository. Search then changes
only the active ordered configuration while the payload bytes, ordinary
statistics, workload, truth binding, and planner remain fixed. PostgreSQL's
native selectivity machinery consumes the active payloads; no replacement
estimator is introduced.

\advisor is the central system artifact. It captures a typed
\texttt{AdvisorSnapshot}, derives workload-relevant native candidates, performs
singleton profiling and bounded Greedy ADD search against independently bound
truth, and emits an ordered Recommendation. That Recommendation is reviewed
and deployed through stock PostgreSQL \texttt{CREATE STATISTICS} followed by
\texttt{ANALYZE}; the patched server is a design-time substrate, not a
production dependency. The current implementation is deliberately scoped to
single-table selection workloads and two-column MCV and dependency candidates.

The paper makes three contributions:

\begin{enumerate}
  \item \textbf{Catalogless native-statistics what-if.} A PostgreSQL
  design-time mechanism registers native payloads and activates ordered
  hypothetical configurations without repeated physical DDL or \texttt{ANALYZE}.
  \item \textbf{Workload-aware native-statistics Advisor.} An offline pipeline
  turns a frozen sample and workload into relevant candidates, native payloads,
  truth-based utility profiles, bounded Greedy ADD search, and a reviewable
  ordered Recommendation.
  \item \textbf{Effectiveness and transfer evidence.} A four-dataset study
  measures estimation quality, same-generator held-out behavior, sample-to-full
  transfer, mechanism fidelity, heuristic comparisons, practicality, bounded
  ordering effects, and qualified native-realization variability.
\end{enumerate}

The five research questions are: RQ1, effectiveness; RQ2, sample-to-full-data
transfer; RQ3, hypothetical-mechanism fidelity under controlled equivalent
physical realizations; RQ4, advisor necessity through search ablations; and
RQ5, practicality. Exact truth is a separate evaluation input. Current source
contracts admit either a production-exact source collected through a restricted
read-only repeatable-read source view, or authoritative external labels
imported with provenance and binding validation. The confirmatory AreCEL policy selects the latter source kind for
all four datasets; Census13 has a one-time 10,000-query equivalence audit
against an existing production-exact canary, while future canonical runs do
not repeat that expensive collection. Production exact execution remains an
independent validation and cost path.

The central claims are intentionally conditional. A recommendation optimizes
the evaluated membership, not necessarily the union of that membership with
arbitrary externally managed production statistics. Existing production
extended statistics remain outside advisor ownership: the advisor does not
silently drop, rename, replace, or reconcile them. A DBA decides whether such
objects remain, are removed, are replaced, or coexist. Historical RQ1a outputs
remain preliminary where their evidence status says so; the matched RQ1a
campaign, four RQ1b children, RQ2 transfer campaign, and RQ3 fidelity checks
are reported only within their declared scopes. RQ4 and RQ5 remain qualified
because the fixed-budget study was cancelled, Native \texttt{ANALYZE} stability
is qualified post-hoc evidence, and end-to-end cost gaps remain explicit.
The v2 readiness review does not retroactively reassign historical artifacts
to a new freeze.

The rest of the paper defines the fixed-payload design problem, describes the
what-if mechanism and Advisor pipeline, and evaluates the three contributions
through five research questions. Results retain all declared qualifications:
sample-to-full transfer is empirical, Greedy is not globally optimal, physical
ordering comparisons can be confounded, Native \texttt{ANALYZE} v2 is
post-hoc, and RQ5 does not establish complete production cost.
