\subsection{Capture and snapshot}

Production capture records an \texttt{AdvisorSnapshot}: schema identity,
relation identity, ordinary-statistics state, a portable fixed sample, and the
workload representation. In the current contract this is exactly $(\Sigma,S,P,W)$;
truth is not added to the snapshot. An optional companion
\texttt{GroundTruthSet} is bound to the sealed snapshot digest and workload ID.
The capture transaction is read-only and uses an explicit repeatable-read
acquisition transaction. A production-exact companion may count only the
supported self-contained simple-selection workload queries in that source
view; the counts can still be expensive. An authoritative external companion
is validated against the snapshot/workload binding and records external
provenance without claiming advisor execution.

\subsection{Sample database and native materialization}

The typed sample is loaded into a sample database with the same relevant schema
and ordinary-statistics policy. Candidate native statistics are materialized
using PostgreSQL's own \texttt{ANALYZE} machinery from the sample. The Advisor
stores the resulting payload bytes in a validated native repository with one
ordinary-statistics fingerprint and one payload record per candidate. The
\texttt{GroundTruthSet} does not enter this construction path: it is consumed
only after planner estimates are produced, to evaluate utility.

\subsection{Sandbox, search, and recommendation}

The patched PostgreSQL backend maintains a backend-local repository of
hypothetical definitions and payloads. The Advisor activates one ordered
configuration at a time, obtains planner estimates, and passes those estimates
together with the independent GroundTruthProvider to utility evaluation. The
same weighted objective is used for singleton profiling and bounded Greedy ADD
search over the frozen candidate universe. The resulting Recommendation
contains native deployment statements and the order derived from the frozen
singleton precedence profile.

\subsection{Stock deployment and ownership}

Deployment uses stock PostgreSQL \texttt{CREATE STATISTICS} followed by one
final \texttt{ANALYZE ``schema'' . ``relation'';} for a non-empty
recommendation. This refreshes ordinary relation statistics, builds the new
advisor-managed objects, and may also rebuild payloads for externally managed
objects on the same relation. It does not transfer ownership of those
objects. Existing production extstats are outside advisor ownership; the
advisor neither models the complete set nor performs reconciliation or garbage
collection. This is a production-oriented, DBA-controlled contract rather than
a claim of production readiness.
